# Technical documentation checklist for firmware teams

A working list of what an EU technical file is expected to contain for a connected device, and where each item comes from inside a firmware project.

**This is not legal advice.** It is a practical starting point written by engineers for engineers. Check every line against the official texts and, for anything that matters, against a lawyer or a notified body.

Sources: Cyber Resilience Act (Regulation (EU) 2024/2847) and Product Liability Directive (EU) 2024/2853.

---

## The dates that drive this

| Date | What applies |
| --- | --- |
| 11 September 2026 | Reporting of actively exploited vulnerabilities within 24 hours |
| **9 December 2026** | Product Liability Directive applies — software and firmware are products under strict liability |
| 11 December 2027 | Cyber Resilience Act applies in full: essential requirements, conformity assessment, CE marking, SBOM |

---

## 1. Product identity

- [ ] Product name, model, variants and versions covered by this file
- [ ] Intended purpose and reasonably foreseeable misuse
- [ ] Hardware platform: MCU family, board revisions
- [ ] Firmware versions in scope, and the exact commit each one was built from
- [ ] Support period you commit to, and where it is published

*Where it comes from:* release tags, build metadata, the product page.

## 2. Design and development

- [ ] Architecture description: tasks, interfaces, external communications
- [ ] Security-relevant design decisions and why they were taken
- [ ] Development process description, including which tools write code
- [ ] **If an AI coding assistant is used: how its output is reviewed before it ships**
- [ ] Toolchain and versions used to produce the released binary

*Where it comes from:* architecture decision records, your build configuration, your process description.

> Most teams discover this is the thinnest part of their file. 89% of embedded teams already use coding assistants; far fewer can show what the assistant wrote and who checked it.

## 3. Risk assessment

- [ ] Cybersecurity risk assessment for the product
- [ ] Threats considered, and mitigations chosen per threat
- [ ] Residual risks accepted, and who accepted them
- [ ] The date it was last reviewed, and the trigger for the next review

*Where it comes from:* a threat model document, reviewed per release, not per project.

## 4. Components and supply chain

- [ ] Software bill of materials covering top-level dependencies, in a machine-readable format
- [ ] Third-party and open-source components with versions and licences
- [ ] How you learn a component has a new vulnerability
- [ ] Due diligence on components you did not write

*Where it comes from:* the build itself. Zephyr emits SPDX during the build; do not hand-maintain this list.

## 5. Verification

- [ ] Test reports for the released version, not a previous one
- [ ] Static analysis results and how findings were handled
- [ ] Coverage figures, with the standard you hold yourself to
- [ ] Hardware-in-the-loop or field test evidence where relevant
- [ ] Evidence that the tests ran against the binary you shipped

*Where it comes from:* CI artefacts. If they are not retained per release, they do not exist for this purpose.

## 6. Vulnerability handling

- [ ] A documented process for receiving reports (a published contact)
- [ ] Triage and remediation timelines you commit to
- [ ] Security update mechanism, and whether updates are automatic
- [ ] A changelog of security fixes
- [ ] The 24-hour reporting path for actively exploited vulnerabilities, with named owners

*Where it comes from:* a SECURITY.md, a monitored inbox, and a rehearsed procedure.

## 7. Conformity

- [ ] Which conformity assessment route applies to your product class
- [ ] EU declaration of conformity, signed, with a named signatory
- [ ] CE marking applied correctly
- [ ] The file retained and available for the required period

*Where it comes from:* your legal and quality process, not your repository.

## The quick self-check

Answer these out loud. The uncomfortable ones tell you where to start.

1. If a regulator asked today, how long would assembling this file take — hours, days or weeks?
2. For the last release you shipped: can you say which changes an AI assistant wrote?
3. Can you show who reviewed them, by name, with a date?
4. Is your SBOM generated by the build, or maintained by a person?
5. Are your test reports kept per release, or overwritten by the next run?
6. If a device fails in the field in 2027, what do you hand over?

If question 1 is "weeks" and questions 2 and 3 are "we can't", you are not unusual — you are the median team. That gap is the reason this checklist exists.

## Generating most of this automatically

[Dossier](https://github.com/adsalmohandis-blip/dossier) is a free, local, MIT-licensed CLI that records items 2 and 5 as you work — what the agent wrote, which gates passed, who approved — and produces a verifiable bundle per release.

It does not write your risk assessment and it does not grant you anything. It fills the parts that come from the repository, which are the parts that are hardest to reconstruct afterwards.

```bash
npx dossier-cli init
```
